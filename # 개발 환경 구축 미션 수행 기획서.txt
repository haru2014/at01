# 개발 환경 구축 미션 수행 기획서

**프로젝트명: Dev-Workstation – 내 컴퓨터에 개발자용 '작업실' 꾸미기**

**개발 유형:** 시스템 환경 구축 및 컨테이너 가상화 실습  
**개발 방식:** 개인 프로젝트 / CLI 기반 단계별 구축 및 검증  
**개발 환경:** Windows 11, PowerShell / Git Bash, Docker Desktop (또는 OrbStack), Git, GitHub, VS Code  

---

## 1. 프로젝트 개요

### 1.1 기획 배경
개발의 출발점은 단순한 코드 작성이 아니라, 코드가 안전하고 일관되게 동작할 수 있는 '실행 환경'을 마련하는 데 있다.  
본 프로젝트는 특정 개인 PC 환경에 종속되어 발생하는 "내 컴퓨터에서는 잘 되는데 왜 서버나 동료 컴퓨터에서는 안 될까?"라는 고질적인 문제를 해결하는 데 목적이 있다.  

리눅스 CLI(터미널), Git/GitHub(버전 관리 및 협업), Docker(컨테이너 가상화)를 연계하여 환경을 직접 구축함으로써, 팀원 누구나 동일한 방식으로 실행·배포·디버깅할 수 있는 재현 가능한(Reproducible) 개발 워크스테이션을 구성한다.

### 1.2 프로젝트 목표
- **리눅스 CLI 기반 파일 시스템 및 권한 제어**: 상대·절대 경로 탐색 및 755/644 권한 구조의 완전한 이해
- **재현 가능한 실행 환경 컨테이너화**: Docker 엔진 구조 이해 및 Dockerfile을 활용한 커스텀 웹 서버 이미지 빌드
- **격리된 네트워크 및 포트 포워딩 검증**: 호스트-컨테이너 간 포트 매핑 구조 이해 및 다중 포트 접속 검증
- **스토리지 아키텍처 검증**: 바인드 마운트(실시간 변경 반영)와 Docker 볼륨(데이터 영속성 유지)의 차이점 실증
- **Git & GitHub 기반 버전 관리 및 보안 준수**: SSH 연동, 의미 있는 커밋 히스토리 관리, 민감 정보(토큰/키) 완벽 격리
- **기술 문서화 및 트러블슈팅 역량 확보**: 실행 로그와 증빙 스크린샷 기반 README 작성 및 문제 해결 과정(최소 2건 이상) 명문화

## 3. 세부 실습 및 기술 설계

### 3.1 터미널 및 권한 실습 설계
- **경로 탐색**: 현재 작업 디렉터리(`pwd`), 절대 경로(`/` 기준) 및 상대 경로(`.`, `..`)를 활용한 파일 탐색
- **파일/디렉터리 조작**: `mkdir -p`, `touch`, `cp -r`, `mv`, `rm -rf`, `cat`을 통한 디렉터리 구조 구축
- **권한 실험**:
  - 실습 대상: 파일 1개(`test_file.txt`), 디렉터리 1개(`test_dir/`)
  - 시나리오: 기본 권한 확인 -> `chmod 644`/`chmod 755` 적용 -> 실행 권한 박탈 및 접근 실패 테스트 -> 복구 후 전/후 비교 기록

### 3.2 Docker 컨테이너 및 커스텀 웹 서버 설계
- **베이스 이미지 선택**: 경량화 및 프로덕션 친화적인 `nginx:alpine` 채택
- **커스텀 포인트**:
  1. 커스텀 인덱스 페이지(`site/index.html`) 제작 (미션 목표, 본인 정보, 컨테이너 정보 표시)
  2. 환경 변수(`ENV APP_ENV=production`, `APP_PORT=80`) 설정
  3. 컨테이너 메타데이터 라벨(`LABEL`) 정의
- **Dockerfile 명세**:
  ```dockerfile
  FROM nginx:alpine
  LABEL maintainer="haru2014"
  LABEL description="Codyssey Mission 01 Custom Nginx Web Server"
  ENV APP_ENV=production
  COPY ./site /usr/share/nginx/html
  EXPOSE 80
  CMD ["nginx", "-g", "daemon off;"]
  ```

### 3.3 포트 매핑 및 스토리지 검증 설계
- **포트 매핑 (다중 포트 검증)**:
  - 1차: `docker run -d -p 8080:80 --name web-8080 my-web:1.0`
  - 2차: `docker run -d -p 8081:80 --name web-8081 my-web:1.0`
  - 검증: 브라우저(`http://localhost:8080`, `http://localhost:8081`) 접속 및 `curl` 응답 확인
- **바인드 마운트 (개발 편의성 검증)**:
  - 명령: `docker run -d -p 8082:80 -v ${PWD}/site:/usr/share/nginx/html --name web-mount my-web:1.0`
  - 절차: 호스트의 `index.html` 내용 수정 -> 브라우저 새로고침 -> 이미지 재빌드 없이 내용 즉시 변경 확인
- **볼륨 영속성 (데이터 보존 검증)**:
  - 볼륨 생성: `docker volume create mission_data`
  - 1단계: 볼륨을 마운트한 임시 컨테이너(`data-worker-1`) 실행 후 `/data/persist.txt` 파일 생성
  - 2단계: 컨테이너 강제 삭제 (`docker rm -f data-worker-1`)
  - 3단계: 동일 볼륨을 마운트한 신규 컨테이너(`data-worker-2`) 생성 후 `/data/persist.txt` 내용 조회
  - 결과: 컨테이너가 영구 소멸되어도 데이터가 온전히 보존됨을 증명

## 6. 트러블슈팅 시나리오 계획 (최소 2건)

### [사례 1] GitHub 원격 푸시 거부 오류 (`non-fast-forward / unrelated histories`)
- **문제 현상**: 로컬에서 `git init` 후 커밋한 상태에서 원격 저장소(`haru2014/at01`)로 `git push` 시도시 `[rejected] main -> main (non-fast-forward)` 오류 발생
- **원인 분석**: GitHub 웹에서 저장소 생성 시 기본 `README.md`가 생성되어 원격에 이미 초기 커밋(`f985cbd`)이 존재하였고, 로컬의 초기 커밋(`4a46235`)과 뿌리(Root)가 달라 Git이 병합을 거부함
- **해결 방안**:
  1. `git fetch origin`을 통해 원격 브랜치 히스토리 수신
  2. `git rebase origin/main`을 실행하여 원격의 `Initial commit` 위에 로컬의 커밋을 단일 선형 히스토리로 재배치
  3. `git push -u origin main`으로 충돌 없이 푸시 완료
- **교훈**: 원격 저장소 생성 시 템플릿 파일이 포함되어 있을 경우 `clone`을 먼저 하거나, `rebase` 전략을 통해 히스토리를 정렬해야 함

### [사례 2] 포트 충돌(Port Conflict) 또는 권한 제한 발생 시 대처
- **문제 현상**: Docker 컨테이너 실행 시 지정한 호스트 포트(예: 8080)가 이미 다른 프로세스에 의해 점유되어 컨테이너 기동 실패 (`bind: address already in use`)
- **원인 분석**: 로컬 PC의 기존 웹 서버, 개발용 서버 또는 이전 Docker 컨테이너가 동일 포트를 선점하고 있음
- **해결 방안**:
  1. `Get-NetTCPConnection -LocalPort 8080` (PowerShell) 또는 `docker ps`로 점유 프로세스/컨테이너 확인
  2. 미사용 중인 컨테이너는 `docker stop`/`docker rm`으로 정리
  3. 필요시 호스트 포트를 8081, 8082 등 대체 포트로 변경하여 포트 매핑 수행
- **교훈**: 호스트 포트는 공유 자원이므로 포트 충돌 방지를 위한 포트 할당 테이블 관리 및 프로세스 점검 습관 필수

## 7. 핵심 개념 질의응답 (Q&A) 준비 계획

평가 및 과제 목표에서 요구하는 6대 핵심 질문에 대해 명확한 근거를 바탕으로 기술 문서에 서술한다.

1. **절대 경로 vs 상대 경로**
   - 절대 경로: 루트 디렉터리(`/` 또는 `C:\`)를 기점으로 파일의 고유한 전체 위치를 명시 (예: `/home/user/at01/site`)
   - 상대 경로: 현재 작업 디렉터리(`.` 또는 `pwd`)를 기준으로 대상을 상대적으로 지정 (예: `./site/index.html`, `../parent_dir`)
2. **파일 권한 체계 (r/w/x, 755 vs 644)**
   - 8진수 표기법: Read(4), Write(2), Execute(1)의 합산.
   - 755 (`rwxr-xr-x`): 소유자는 읽기/쓰기/실행 모두 가능, 그룹 및 일반 사용자는 읽기/실행만 가능 (주로 실행 파일, 디렉터리에 적용)
   - 644 (`rw-r--r--`): 소유자는 읽기/쓰기 가능, 그룹 및 일반 사용자는 읽기만 가능 (주로 일반 텍스트 문서, 정적 리소스에 적용)
3. **기존 베이스 이미지 기반 커스텀 이미지 제작 원리**
   - 베이스 이미지의 계층(Layer) 위에 필요한 설정, 환경 변수(`ENV`), 애플리케이션 파일(`COPY`)을 레이어 형태로 추가하여 새로운 독립 실행 이미지를 패키징
4. **포트 매핑(Port Forwarding)이 필수적인 이유**
   - Docker 컨테이너는 호스트 OS로부터 격리된 독립적인 사설 가상 네트워크 네임스페이스(Virtual Network)를 갖는다.
   - 외부(호스트 브라우저)에서 컨테이너 내부 서비스에 접근하려면 호스트의 특정 포트로 들어온 트래픽을 컨테이너 내부 포트로 연결해 주는 포트 포워딩(`-p <호스트포트>:<컨테이너포트>`)이 필수적이다.
5. **Docker Volume과 바인드 마운트의 영속성 원리**
   - 컨테이너의 Writable 레이어는 컨테이너 삭제 시 함께 파괴된다(Stateless).
   - Docker Volume은 Docker가 관리하는 호스트 저장 영역(`/var/lib/docker/volumes/`)에 데이터를 보관하므로 컨테이너 수명 주기와 분리되어 데이터가 영구 보존된다.
   - 바인드 마운트는 호스트의 특정 절대 경로 디렉터리를 직접 공유하여 개발 중 실시간 코드 반영에 유리하다.
6. **Git vs GitHub의 본질적 차이**
   - Git: 로컬 컴퓨터에서 코드의 변경 이력(버전)을 기록하고 브랜치를 관리하는 분산 버전 관리 시스템(DVCS) 도구
   - GitHub: Git으로 관리되는 로컬 저장소를 클라우드에 업로드하여 원격 백업, 코드 리뷰, 이슈 추적, 협업을 가능케 하는 웹 기반 호스팅 플랫폼
